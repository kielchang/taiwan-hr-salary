## 5. token 副本同步守衛

理想情況是文件站直接吃 token 產物（`@import` 或 alias），這樣根本沒有副本。
上游自己就是這樣做的，所以沒有這個問題。

但**很多宿主專案做不到**：文件站是另一個框架（Docusaurus、VitePress），
有自己的 CSS 管線與樣式重置，直接匯入產物會與站台主題打架，
或是產物裡的深色選擇器（`.dark`）與文件站的深色開關（`html[data-theme="dark"]`）對不上。

這時務實的做法是**留一份副本**，並且立刻替它配一支守衛：

```ts
it("token 副本涵蓋樣式設定引用的全部變數", () => {
  const config = read("tailwind.config.js");
  const copy   = read("docs-site/src/css/tokens.css");

  const wanted = new Set(
    [...config.matchAll(/var\((--[a-z0-9-]+)\)/g)].map((m) => m[1])
      // 執行期由第三方元件注入的變數不是設計 token，不需入副本
      .filter((v) => !v.startsWith("--radix"))
  );
  expect(wanted.size).toBeGreaterThan(10);        // 守衛本身沒有空轉
  for (const v of wanted) expect(copy).toContain(`${v}:`);
});
```

三個設計重點：

| 重點 | 為什麼 |
| --- | --- |
| 以**樣式設定實際引用的變數**為準，不是以來源檔的變數清單為準 | 來源檔會有還沒被用到的 token，強迫副本全帶只會製造噪音 |
| **排除執行期注入的變數** | 第三方元件會在 runtime 注入 `--*` 變數，它們不是設計 token，永遠不會出現在副本裡 |
| 斷言「想要的集合不是空的」 | 正則寫錯時 `wanted` 會是空集合，迴圈一次都不跑，**守衛變成永遠綠燈** |

<Rules>
  <Do><p>副本檔開頭寫清楚<strong>它是副本、來源在哪、由哪支守衛盯著</strong>。</p></Do>
  <Dont><p>不要以為「反正加 token 的時候會記得同步」。加 token 的人在改的是元件，
  他的腦子裡沒有文件站。沒有守衛的話，症狀會是文件站的活範例<strong>顏色慢慢跑掉</strong>——
  而那是最不容易被回報的一種壞掉，因為它看起來只是「有點怪」。</p></Dont>
</Rules>

## 6. 文件掛鉤守衛：引用的東西必須存在

文件一旦開始嵌入真元件（story、示意流程、範例畫面），
它就對元件庫產生了**以字串為鍵的相依**：

```
文件寫  <StoryFrame id="元件-資料表--篩選" />
        <MockFlow  name="batch-dispatch" />
                    ↑ 這兩個字串沒有型別檢查，改名不會有人告訴你
```

守衛：把文件裡引用的 id／name 全部收集起來，逐一比對是否存在。

```ts
// story id 由 stories 檔的 meta.title + export 名推導（沿用 Storybook 的 id 規則）
const validIds = collectStoryIds("src/components/**/*.stories.tsx");
for (const f of docFiles)
  for (const [, id] of read(f).matchAll(/<StoryFrame[^>]*id="([^"]+)"/g))
    expect(validIds.has(id), `${f} 引用不存在的 story：${id}`).toBe(true);
```

**失敗訊息要指出是哪個檔案引用了哪個不存在的鍵。**
這支守衛紅的時候，動手的人通常正在改元件、對文件毫無概念——
訊息要能讓他不必理解文件站就知道該去改哪一行。

順帶做兩件事：

- **禁止回歸**：把已經廢除的做法（例如截圖素材）也寫成斷言。
  「不要再用截圖」寫在規範裡會被遺忘，寫成測試不會。
- **正向下限**：斷言文件至少嵌了 N 個視覺輔助，確保守衛不是在對空集合微笑。

## 7. 雙站部署：路徑過濾與它的例外

應用程式與文件站各自獨立部署，用路徑過濾避免互相牽動：

```yaml
# 應用程式：文件變更不重佈
paths-ignore:
  - "docs-site/**"

# 文件站：文件變更才重佈……
paths:
  - "docs-site/**"
  # ……但元件變更也必須重佈（例外，見下）
  - "src/components/**"
  - ".storybook/**"
```

前半是效率問題（改一個錯字不必重建整個應用程式），後半才是重點：

<Callout variant="warning" title="容易漏掉的例外">
  **文件站內嵌元件與 story，所以元件變更必須觸發文件站重佈。**
  只設 `paths: ["docs-site/**"]` 的話，元件改版後文件站不會重建，
  裡面嵌的仍是舊版元件——文件與現行介面**當場脫鉤**，
  而這件事沒有任何測試看得見，因為兩邊各自都是綠的。
</Callout>

這就是為什麼「零截圖」的承諾（元件改版，示意圖自動跟上）**必須由 CI 設定來兌現**。
承諾寫在文件裡，兌現寫在 workflow 裡；只有前者沒有後者，承諾是假的。

還有一個小陷阱：兩個部署寫入的是**同一個發佈分支的不同子目錄**。
它們要共用同一個 concurrency group，否則同時觸發時會互相覆蓋——
症狀是「明明部署成功了，但站上還是舊的」。

## 判準：什麼時候需要一支新守衛

上面這些看起來各不相干，但判準只有一條：

<Callout variant="info" title="判準">
  **同一份事實只要存在於兩個地方，就需要一支守衛。**
</Callout>

| 兩個地方 | 守衛 |
| --- | --- |
| token 來源 ↔ 文件站副本 | 副本涵蓋率 |
| 元件庫 ↔ 文件引用的 story id | 掛鉤存在性 |
| 元件庫 ↔ 已部署的文件站 | CI 路徑過濾 |
| 淺色 token ↔ 深色 token | 成對檢查（上游第 3 支） |
| 元件檔 ↔ barrel | 覆蓋率（上游第 2 支） |

而最好的守衛，是**讓那份事實只存在一個地方**——
能 alias 就不要複製，能自動推導就不要手寫清單。
守衛是次佳解，用在「消不掉的第二份」上。

# 元件庫邊界治理三件組

> **落地位置**：**不是新增一頁**，而是併進既有的
> `book/docs/6-governance/03-drift-guards.mdx`（一節）與
> `book/docs/6-governance/01-versioning.mdx`（一段）。
>
> **為什麼不新增頁**：上游的〈漂移防護〉已經寫了邊界守衛與 barrel 覆蓋率，
> 〈版本策略〉已經寫了三層獨立版號。再開一頁講「邊界治理」等於把同一件事講兩次，
> 而兩份講同一件事的文件必然會慢慢分歧——這正是設計系統漂移的典型起點。
> 以下只列**上游還沒有的部分**。

---

## 一、把三件事講成一組（框架，非新規則）

上游現在是三條分散的規則。它們其實是同一個承諾的三個面向：
**「這個元件庫可以被原樣搬到別的專案。」**

| 件 | 回答什麼 | 上游現況 |
| --- | --- | --- |
| **Barrel** | 公開範圍到哪裡 | 有守衛（覆蓋率），但沒說 barrel 的**語意**是「對外契約」 |
| **守衛測試** | 邊界有沒有被穿透 | 有（import 白名單） |
| **獨立版號** | 使用者抄的是哪一版 | 有（三層各自版號） |

建議在〈漂移防護〉開頭加一句把三者串起來：

> 這三支守衛不是三條獨立規則，是同一個承諾的三個面向：
> **barrel 說「公開範圍到哪裡」、守衛說「邊界有沒有被穿透」、版號說「你抄的是哪一版」。**
> 少任何一件，另外兩件都會慢慢失效。

理由：分散的三條規則，各自都很容易被「這次先例外一下」繞過。
講成一組之後，繞過任何一條都會明顯地違反同一個承諾。

---

## 二、Barrel 是公開契約，不只是方便的匯出點（新增）

上游的守衛只檢查「新元件有沒有被漏掉」。缺的是另一半：**沒被 barrel 匯出的東西不是公開 API。**

建議在〈2. Barrel 覆蓋率〉之後補：

> ### Barrel 定義的是「公開範圍」
>
> Barrel 有兩個方向的意義，守衛只擋住了其中一個：
>
> - **漏掉**（守衛已擋）：新元件沒進 barrel，會被人繞過 barrel 深層 import
> - **多出來**（守衛擋不住）：不該公開的東西進了 barrel，就再也拿不掉了
>
> 第二種比第一種難救。一旦某個內部輔助元件被匯出，就會有人開始用它，
> 之後任何調整都是 breaking change——而它從來不是你打算支援的東西。
>
> 判準：**這個東西有沒有做出視覺或互動的決策？**
>
> | 進 barrel | 不進 barrel |
> | --- | --- |
> | 有視覺／互動決策、任何專案都能用 | 綁定特定業務語彙（欄位名、狀態機、流程） |
> | 只依賴 token 與彼此 | 需要應用層的狀態、路由、資料來源 |
> | 有 story、有文件頁 | 只是把幾個元件拼在一起的私有便利函式 |
>
> **Do**：拿不定主意就先不匯出。加進 barrel 是 minor 版本，拿掉是 major。
> **Dont**：不要為了「反正遲早會用到」預先匯出。預先匯出的東西沒有文件、
> 沒有 story，卻已經是契約了。

## 三、第五支守衛：禁止原始調色盤字面色（新增）

上游有四支守衛（邊界、barrel、token、詞彙）。下游多做了一支，**建議上游收**：

```ts
// 元件庫不得出現原始調色盤字面色，狀態色一律走語意 token
const FORBIDDEN_PALETTE =
  /\b(?:border|bg|text|ring|from|to|via|fill|stroke)-(?:amber|emerald|rose|sky|orange|yellow)-\d{2,3}\b/g;

for (const file of shippedFiles) {
  const hits = [...readFileSync(file, "utf8").matchAll(FORBIDDEN_PALETTE)];
  expect(hits, `${file} 請改用語意 token（如 text-success / border-edit）`).toEqual([]);
}
```

### 為什麼 token 守衛擋不到這個

上游的 token 守衛檢查的是「token 本身完不完整、淺深有沒有成對」。
它**檢查不到「有人根本沒用 token」**——直接寫 `bg-amber-100` 的那一行，
在 token 守衛眼裡完全不存在。

而這正是最容易發生的漂移：趕時間的時候，
`bg-amber-100` 比「先去查該用哪個語意 token」快，
而且當下看起來一模一樣。等到有人換主題或切深色，
才發現有十幾處顏色不會跟著變——那時已經找不出是誰在哪次改的了。

**特別要盯琥珀**：`--edit` 是保留色（[ADR-0002](/adr)）。
一旦有人用原始色碼寫了一個「順便也是琥珀色」的高亮，
「已改動未送出」這個訊號就被稀釋了，而稀釋是不可逆的——
使用者一旦學到「琥珀有時候沒有意義」，就再也不會相信它。

> **Do**：狀態色只用 `success` / `warning` / `info` / `danger` / `edit`。
> **Dont**：不要在元件庫裡出現任何 `-500` `-100` 這種色階數字。
> 它們在應用層或許還可接受，在元件庫裡一定是漏網之魚。

## 四、版號放在元件庫**內部**（補一段）

〈版本策略〉已經說明三層各自獨立版號。缺的是一個實作細節：
版號應該是**元件庫內部的一個檔案**，不是只寫在 `package.json`。

```ts
// packages/react/src/version.ts
export const KIT = { name: "…", version: "0.18.0" } as const;
```

三個理由：

1. **切割時跟著走**：整個資料夾複製到別的專案，版號自己帶著，不必翻 `package.json`
2. **可以顯示在畫面上**：Storybook 首頁掛一個版號徽章，
   下游一眼就知道自己看的是哪一版——這是「我抄的是哪一版」最直接的答案
3. **可以被守衛測試讀到**：一支斷言就能保證版號存在且是合法 SemVer，
   不會出現「忘記 bump」的沉默失敗

建議在〈為什麼元件版號與 token 分開〉之後補一句：

> 版號檔放在元件庫**裡面**（`src/version.ts`），不只是 `package.json`。
> 元件是要被複製走的——複製走之後，`package.json` 留在原地，
> 而使用者最需要的資訊正是「我手上這份是哪一版」。

# 設計上游：doping-design-book

本專案的介面設計**不是自己說了算**——設計語言與操作邏輯的單一真實來源在上游：

<https://github.com/kielchang/doping-design-book>

| 檔案 | 用途 |
|---|---|
| [`conformance.md`](conformance.md) | **符合性台帳**：每個本地元件是「遵循／自製／刻意偏離」 |
| [`proposals/`](proposals/) | 給上游的改進提案（走 PR，合併後才動本地） |
| `../../scripts/design-book.sh` | 一行取得／閱讀上游規範 |

## 🔒 唯讀鐵律

**本專案不得寫入 doping-design-book。**

不只是規範——環境上也做不到（push 回 403）。要改上游一律走：

```
在這裡發現問題 → 寫 proposals/ 提案 → 由人帶去上游開 PR
   → 上游確認並合併 → 才回頭更新 conformance.md 與本地實作
```

**「等到有確認修改才能動」** 是這條流程的重點：未合併的提案不得先行實作，否則兩邊會各走各的。

## 怎麼讀上游

```bash
./scripts/design-book.sh                                  # 取得／更新（唯讀，放在 repo 外部）
./scripts/design-book.sh --list                           # 列出所有章節
./scripts/design-book.sh --show 4-patterns/03-hard-lock    # 直接印出某篇規範
```

上游會被放在 `../doping-design-book`（**repo 外部**，不進本專案版控）。容器重建後重跑一次即可。

取得後**先讀上游根目錄的 `AGENTS.md`**——那是上游自己寫的一頁式取用契約（三層各自的改動權、
registry 指令、什麼不能改）。本檔是「本專案這一側」的規則，兩者互補。

### 環境限制（先知道，免得走冤枉路）

| 途徑 | 可用性 |
|---|---|
| `git clone` / `fetch` 讀取 | ✅ 可用（上面的腳本走這條） |
| GitHub Pages 文件站（WebFetch/curl） | ❌ 403，本環境 proxy 擋 github.io |
| GitHub MCP 讀該 repo | ❌ session scope 僅授權本 repo |

## 上游的三層結構（相依強度刻意遞減）

| 層 | 內容 | 本專案取用方式 |
|---|---|---|
| `packages/tokens` | 設計 token（色彩語意、間距、字級、動態…） | **未來**唯一建議 npm 安裝的一層（第 2 階段） |
| `packages/react` | React 參考實作 | 目前**不裝**；本地 `src/components` 是平行實作，靠台帳對齊 |
| `book/docs/4-patterns` | 操作模式（問題→做法→取捨→反例） | **現在就該讀**——設計判斷的依據 |

理由：**元件一定會被改，token 幾乎不會。**

## 怎麼避免兩個 repo 打架

1. **結構上不可能衝突**：兩 repo 各自獨立版控，無 submodule、無共用工作區、無自動同步。
2. **單向唯讀**：本專案只讀上游，永不寫入。
3. **上游更新不自動套用**：拉取 → 對台帳逐列評估 → 決定是否跟進 → 更新台帳。升級是**決定**，不是意外。
4. **反向變更走提案 PR**：確認合併後才動本地。
5. **兩本帳分工**：[`docs/ui-kit/CHANGELOG.md`](../ui-kit/CHANGELOG.md) 記「本地改了什麼」；[`conformance.md`](conformance.md) 記「與上游的關係」。

## 離線摘要（沒網路也能做判斷）

> 完整內容請讀上游；以下是最常用的判斷依據。

### 色彩＝語意，不是色票

- 狀態語意：`success` / `warning` / `info` / `danger`——**不要**直接用綠紅黃藍的原始色碼
- 欄位語意：可編輯 vs 唯讀（本專案＝`.col-input` vs 純文字／`.col-formula`）
- **琥珀 `--edit` 是保留色**：專屬「已改動未送出」，不得挪作他用（否則使用者學到的意義會被稀釋）
- 變異顯示：▲▼＋文字＋色**三重編碼**，不只靠顏色（色盲與灰階列印仍可辨義）

### 10 則操作模式（一句話版）

| 模式 | 一句話 | 反例 |
|---|---|---|
| 唯讀逐欄編輯 | 點擊才進編輯、改動標色、還原先確認 | 整頁都是輸入框，看不出哪裡被改過 |
| 情境化申請單 | 挑情境→只填該情境欄位＋必填原因 | 一張大表塞滿所有欄位，找不到要改哪個 |
| 硬鎖定與明確解鎖 | 確認＝凍結，要改必須明確解鎖 | **編輯自動解除確認**（使用者不知道自己打回了已核准狀態） |
| 稽核與回復 | 結構化 before/after，可回復者才給回復鈕 | 只記「某某改了某某」，無法還原 |
| 生效日版本化設定 | 改參數指定生效月，不回溯污染歷史 | 就地改費率，上個月的已申報數字跟著變 |
| 引導式導覽 | 聚光＋**可縮小**（免得擋住要操作的地方） | 導覽卡蓋住按鈕，照著做卻按不到 |
| 資料表標準 | 搜尋／篩選／排序／分頁／合計／凍結首欄／CSV 一次到位 | 每個畫面手刻表格，改樣式要改十處 |
| 空狀態與狀態徽章 | 沒資料要說「為什麼沒有、下一步做什麼」 | 空白畫面 |
| 列印與匯出 | 隱藏站台外殼、不跨頁截斷、背景跟隨主題 | 印出來有導覽列、元件被切一半 |
| 零截圖文件示意 | 用真元件排版當示意圖，重點聚光其餘留白 | 截圖——UI 一改就過期 |

### 無障礙門檻

- 觸控目標 **≥44px**（`.tap-target` / `.tap-target-y`）
- 語意**不只靠顏色**傳達
- 鍵盤可達、焦點可見；鎖定欄位仍可聚焦（螢幕報讀器要唸得到原因）
- 尊重 `prefers-reduced-motion`

## 新增或修改元件時

1. 先查上游有沒有：`./scripts/design-book.sh --list`
2. **有** → 遵循它，在 [`conformance.md`](conformance.md) 記一列「遵循」
3. **沒有** → 自製，記一列「自製」；若具通用性（三次法則：2～3 個專案會用到）→ 寫 [提案](proposals/)
4. **要跟上游不一樣** → 記「刻意偏離」並**寫清楚原因**（沒原因＝待修）
